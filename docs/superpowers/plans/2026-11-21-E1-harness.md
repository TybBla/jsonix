# E1 — Harness jakości: plan etapu

> Dla agentów: realizuj TYLKO swoje zadanie, w TDD (najpierw test, potwierdź, że pada; potem kod). Pracujesz w osobnym git worktree; commituj na swojej gałęzi w konwencji `typ(zakres): opis` z linią `Co-Authored-By: Claude <noreply@anthropic.com>`. Nie pushuj. Nie zmieniaj plików spoza listy „Pliki”. Raport końcowy: lista plików, ostatnia linia `pytest`, hash commitu.

**Cel:** automat, który mierzy każdą zmianę i blokuje regresje, zanim powstanie właściwa logika.
**Roadmapa:** `docs/superpowers/plans/2026-11-21-roadmap-produkcyjna.md` (E1). **Spec:** `docs/superpowers/specs/2026-11-21-odwolania2json-design.md`.
**Gałąź etapu:** `etap/E1-harness`. Zadania na gałęziach `etap/E1/<id>`.

## Ograniczenia globalne
- Python 3.13+ (lokalnie 3.14), Windows i Linux; ścieżki przez `pathlib`, pliki tekstowe w UTF-8.
- Nie zmieniamy publicznych sygnatur z `odw2json/contracts.py`, `config_loader.py` ani `pipeline.run/process_file`; wolno dodawać parametry opcjonalne.
- Wynikowy JSON ściśle wg szablonów `config/schemas/*.json`; dokument nieznany daje `{}`.
- Testy nie mogą wymagać sieci ani klucza API.

## Na co zwrócić uwagę przy review
1. Gate nie może przepuścić regresji przez zaokrąglenia: porównanie z tolerancją `1e-9`, a spadek o więcej niż tolerancja to błąd.
2. Split musi być deterministyczny i stabilny przy dodaniu nowych spraw (przydział przez hash `sha256(f"odw2json-split-v1:{case}") % 4 == 0` → `holdout`; ok. 25% nowych spraw trafia do holdoutu, przydziały istniejących spraw są stabilne).
3. Tryb `replay` przy braku kasety ma rzucać czytelny błąd, a nie wołać sieci.
4. Na Windowsie konsola cp1250: CLI nie może się wysypać na polskich znakach w logach i wydrukach.
5. CI zielone na obu systemach; Windows ma te same testy co Linux.

### T1 — Splity danych (Haiku, effort low) · fala 1
**Pliki:** `scripts/make_splits.py`, `data/splits.yaml`, `tests/test_splits.py`, `odw2json/splits.py`.
- `odw2json/splits.py`: `load_splits(path: Path = ROOT_DIR/"data"/"splits.yaml") -> dict[str, list[str]]` zwracające klucze `dev`, `holdout`, `negatives` (nazwy katalogów spraw względem `data/train`, np. `przyklad_07`; `negatives` = `["negatywne"]`).
- `scripts/make_splits.py`: przydział sprawy deterministycznie przez hash: `int(sha256(f"odw2json-split-v1:{case}").hexdigest(), 16) % 4 == 0` → `holdout`, inaczej `dev`. Dzięki temu nowe sprawy nie zmieniają starych przydziałów. Zapis posortowanych list do YAML z komentarzem, jak regenerować.
- Testy: wszystkie katalogi `przyklad_*` są dokładnie w jednym z `dev`/`holdout`; holdout ma 10–20 spraw; drugie uruchomienie skryptu daje identyczny plik; dodanie fikcyjnej sprawy nie zmienia przydziału istniejących (test na funkcji przydziału).
- **Done:** testy zielone, `data/splits.yaml` w repo.

### T2 — Kontrakt kształtu wyniku (Sonnet, effort medium) · fala 1
**Pliki:** `odw2json/schema.py`, `tests/test_schema_contract.py`.
- `build_json_schema(template: dict) -> dict`: z szablonu (`DocTypeConfig.template()`) buduje JSON Schema draft 2020-12. Obiekty: `additionalProperties: false`, wszystkie klucze `required`. Listy: `items` z pierwszego elementu szablonu. Liście: dozwolone `null` + typ wnioskowany z danych treningowych lub domyślnie `["string","number","integer","null"]`.
- `validate_output(data: dict, cfg: DocTypeConfig) -> list[str]`: lista błędów (pusta = OK); własna, lekka walidacja kształtu (bez nowej zależności, chyba że `jsonschema` jest uzasadniony — wtedy dopisz do `requirements.txt`). `{}` jest poprawne tylko jako wynik dla dokumentu nieznanego (osobna funkcja `is_unknown_output`).
- Testy kontraktowe: (a) każdy typ z `load_registry()` ma szablon zgodny z samym sobą; (b) **każdy GT JSON** z `data/train/przyklad_*/` przechodzi `validate_output` swojego typu (to dowód, że szablony = format UZP); (c) wynik `pipeline.process_file` dla `przyklad_01` przechodzi walidację; (d) dodatkowy klucz, brakujący klucz albo zły typ kontenera dają błąd.
- **Done:** testy zielone; jeśli (b) ujawni niezgodność szablonu z GT, zgłoś ją w raporcie zamiast naginać test.

### T3 — LLM record/replay (Sonnet, effort medium) · fala 1
**Pliki:** `odw2json/llm.py`, `config/llm.yaml`, `tests/test_llm_replay.py`, `tests/cassettes/.gitkeep`.
- Tryb z `LLM_MODE` (env) lub `config/llm.yaml: mode`: `live` (tylko sieć), `record` (sieć + zapis kasety), `replay` (tylko kaseta; brak → `CassetteMissing` z kluczem i podpowiedzią `LLM_MODE=record`), `auto` (kaseta, jeśli jest, inaczej sieć i zapis). Domyślnie `auto`, a w testach (`PYTEST_CURRENT_TEST`) `replay`.
- Kaseta: `tests/cassettes/<sha256>.json` = `{model, system, user, response, usage, created}`; klucz z `model + system + user + temperature`. Katalog konfigurowalny.
- Licznik zużycia: `LLMClient.usage` sumuje `prompt_tokens`/`completion_tokens`, metoda `usage_report() -> dict`.
- `from_config()` bez klucza API w trybie `replay` nie rzuca (klucz potrzebny tylko w sieci).
- Testy bez sieci, z podmienionym klientem OpenAI (fake obiekt z `chat.completions.create`): record zapisuje kasetę, replay ją czyta bez wołania klienta, replay bez kasety rzuca `CassetteMissing`, auto nagrywa przy braku, usage się sumuje.
- **Done:** testy zielone; zero wywołań sieci w testach.

### T4 — Logowanie i identyfikator przebiegu (Sonnet, effort medium) · fala 1
**Pliki:** `odw2json/logging_setup.py`, `odw2json/pipeline.py`, `odw2json/cli.py`, `tests/test_logging.py`.
- `setup_logging(verbose: bool, log_file: Path | None) -> str` zwraca `run_id` (UTC `YYYYmmddTHHMMSSZ-<6 hex>`); format konsoli czytelny, plik `output/.logs/<run_id>.jsonl` w JSON Lines (`ts, level, run_id, event, file, doc_type, ms`).
- `pipeline.run(..., run_id: str | None = None)`: czas per plik, `run_id` w każdym trace (`"run_id"`), podsumowanie `output/.logs/<run_id>.summary.json` (liczba plików, typy, błędy, łączny czas).
- CLI: `--verbose`, `--log-file`; wymuszenie UTF-8 na stdout/stderr (`reconfigure(encoding="utf-8", errors="replace")`), żeby cp1250 nie wysypywał polskich znaków.
- Testy: run tworzy summary i jsonl; każda linia jsonl to poprawny JSON z `run_id`; trace zawiera `run_id`; CLI w subprocessie z nazwą pliku `zażółć.pdf` kończy się kodem 0.
- **Done:** testy zielone, istniejące testy pipeline bez zmian zachowania.

### T5 — Bramka F1 (Sonnet, effort high) · fala 2 (po T1, T2)
**Pliki:** `eval/gate.py`, `eval/baseline.json`, `tests/test_gate.py`, `eval/README.md`.
- `python -m eval.gate [--split dev|holdout|all] [--update-baseline] [--tolerance 0.0]`: tworzy tymczasowe `input/` z PDF-ów wybranych spraw (+ negatywy), uruchamia `pipeline.run` do katalogu tymczasowego, liczy `eval.score.score_dirs` (tylko wybrane sprawy), sprawdza `schema.validate_output` dla każdego wyniku, porównuje z `eval/baseline.json`.
- Baseline per split: `f1` globalne, `f1` per typ, `f1` per pole, `neg_correct/neg_total`, liczba błędów schematu (musi być 0), liczba błędów klasyfikacji.
- Wynik: tabela różnic (↑/↓), kod wyjścia 1 przy każdym spadku poniżej bazy minus tolerancja, przy błędzie schematu albo wyjątku pipeline; zapis `output/.gate/<split>.json`.
- `--update-baseline` nadpisuje tylko wskazany split i wypisuje różnice.
- Test negatywny harnessu: podmień `extract.extract` (monkeypatch), żeby gubił jedno poprawnie wyciągane pole albo psuł kształt → gate zwraca 1; bez zmian → 0. Testy na małym podzbiorze (2 sprawy + 1 negatyw), oznaczone tak, żeby trwały < 10 s.
- **Done:** testy zielone; `eval/baseline.json` wygenerowany dla `dev` i `holdout` na obecnym kodzie.

### T6 — CI i smoke (Sonnet, effort medium) · fala 3 (po T0–T5)
**Pliki:** `.github/workflows/ci.yml`, `scripts/smoke.ps1`, `scripts/smoke.sh`, `README.md` (sekcja „Jakość i CI”).
- Workflow na push i PR: macierz `ubuntu-latest`, `windows-latest` × Python `3.13`; kroki: `pip install -r requirements-dev.txt` → `ruff check .` → `ruff format --check .` → `pytest -q -m "not live_llm"` → `python -m eval.gate --split dev` → `python -m eval.gate --split holdout` → smoke. Env `LLM_MODE=replay`.
- Smoke: świeży venv w katalogu tymczasowym, `pip install -r requirements.txt`, kopia 1 sprawy + 1 negatywu do tymczasowego `input/`, uruchomienie `start.bat`/`start.sh` z argumentami, sprawdzenie, że powstały 4 JSON-y, a negatyw ma `{}`.
- Job `docker` (tylko ubuntu): `docker build .` musi przejść.
- **Done:** pliki gotowe, `scripts/smoke.ps1` przechodzi lokalnie na Windows; CI zweryfikuje orkiestrator po pushu.
